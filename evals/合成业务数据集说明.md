# 合成业务数据集

`cases/synthetic_business_v1.json` 是预约业务的**确定性合成数据**，用于搭建可重复的测试输入和业务预期。门店、员工、客户、历史选择、价目、排班、已有预约都由生成器创建，不含生产数据，也不代表任何真实门店的分布或经营指标。

## 当前内容

固定随机种子 `20260924`，生成结果包含：

| 数据 | 数量 |
| --- | ---: |
| 门店 | 3 |
| 服务项目 | 5 |
| 技师 | 15 |
| 房间 | 9 |
| 虚构客户 | 30 |
| 已有预约 | 64 |
| 场景用例 | 64 |

场景覆盖可预约时段、缺失服务条件、模糊服务意图、营业时间外、偏好技师不可用、资源冲突、过期方案、重复确认及并发抢占。生成器同时校验门店与客户归属、服务可售范围、技师技能、班次、房间类型、时长缓冲和资源占用冲突。

## 生成和校验

在仓库根目录运行：

```bash
.venv/bin/python -B evals/generate_synthetic_business_data.py
.venv/bin/python -B -m pytest -q -p no:cacheprovider tests/test_synthetic_business_data.py
.venv/bin/python -B -m pytest -q -p no:cacheprovider tests/test_synthetic_business_database.py
```

固定种子会产生相同 JSON。需要临时探索另一份数据时，可使用 `--seed` 和 `--output` 指向独立路径；正式对比实验应固定并记录种子、数据文件摘要、代码版本及模型配置。

## 数据库评测与边界

`tests/test_synthetic_business_database.py` 会把数据映射到 `appointment_test` 下的新隔离 schema，再调用预约领域服务：34 个可预约、营业时间外、偏好技师不可用和资源冲突场景逐条对照数据集 oracle；另选一个并发场景，让两个客户竞争同一资源，验证只产生一个占位和订单、资源区间不重叠、同一确认重放返回同一订单。数据库用例按仓库约定保留独立 schema。

### 真实 Agent 模型评测

真实模型运行器 `evals/run_synthetic_business_agent_eval.py` 会为每个案例建立独立 `appointment_test` schema，使用 AgentScope + DeepSeek 运行原始场景输入，并把任务状态、模型决策、工具结果和数据库增量逐例写入 JSONL 检查点。运行前必须设置 `DEEPSEEK_API_KEY`；脚本拒绝非 `appointment_test` 数据库和非 `test` 环境。报告会记录数据集、工具契约、提示词及关键源码摘要，工具返回里的临时凭据会脱敏。遇到中断时可用 `--resume <JSONL路径>` 从已完成案例后续跑。

运行命令：

```bash
.venv/bin/python -B evals/run_synthetic_business_agent_eval.py
.venv/bin/python -B evals/run_synthetic_business_agent_eval.py --scored-only
.venv/bin/python -B evals/run_synthetic_business_transaction_agent_eval.py
```

首次 64 案例运行使用 `deepseek-flash`、`reception-v3`，共 191 次模型轮次调用；当时 46 个首轮可评分场景有 37 个通过、9 个失败，原始记录和重评分摘要分别见 `evals/reports/synthetic_business_agent_20260924T061304Z.jsonl` 与 `evals/reports/synthetic_business_agent_20260924T061304Z_rescored_summary_20260924T062124Z.json`。诊断发现两类实现问题：模型把用户期望开始时刻生成成一小时查询窗口，覆盖不了 75–90 分钟服务；泛称“放松项目”被模型擅自映射成了具体服务。现已由服务端按可信报价时长扩展精确时段查询窗口，并要求服务槽位匹配本轮用户消息中的唯一目录名称或别名，否则追问。

修复后的全量首轮基线重新运行 46 个可评分场景，**46/46 通过、154 条断言全部通过**，共 148 次模型轮次调用；零占位、零订单、零资源分配。分组结果为可约时段 12/12、缺失服务追问 6/6、模糊服务追问 6/6、营业时间外 6/6、偏好技师不可用 8/8、预约冲突 8/8。另将修复前 9 个失败案例定向复测，9/9 通过、32 条断言通过。全量报告为 `evals/reports/synthetic_business_agent_20260924T065751Z.jsonl`，按业务 oracle 重算的报告为 `evals/reports/synthetic_business_agent_20260924T065751Z_rescored_summary_20260924T070427Z.json`；定向复测摘要为 `evals/reports/synthetic_business_agent_20260924T064140Z_summary_064236.json`。这些结果只描述固定合成数据、模型及提示词版本，不代表真实门店表现。

事务场景由 `evals/run_synthetic_business_transaction_agent_eval.py` 完成多轮验证：6 个方案失效场景（排班变更、报价撤销、候选过期各 2 个）在用户选候选后均被拒绝，未产生新预约；6 个重复确认场景均只创建一笔订单，并用同一幂等键、请求摘要重放原结果；6 个双客户竞争场景均由 PostgreSQL 排他约束裁决为一个成功、一个 `SLOT_CONFLICT`，再确认唯一胜者。真实 Agent 事务流程共 142 次模型轮次调用，18/18 场景通过，报告为 `evals/reports/synthetic_business_transaction_agent_20260924T065355Z.jsonl` 和 `evals/reports/synthetic_business_transaction_agent_20260924T065355Z_summary.json`。

并发 Agent 实测还发现：排他约束拒绝第二个写请求后，失败事务会使外层 SQLAlchemy 会话无法继续记录工具结果。现已在统一工具注册表将每个写工具包进事务保存点，使约束失败只回滚该次工具写入；新增 `test_write_tool_conflict_rolls_back_savepoint_and_keeps_session_usable` 验证外层会话仍可继续读写。首次 64 案例观测、全量首轮复测和事务多轮报告分开保存，不把不同代码版本下的指标拼成一个回归分数。`tests/test_synthetic_agent_eval_scoring.py` 覆盖 oracle 评分规则。已有的 `full_booking_pilot_v1.json` 是另一组演示服务案例，两套数据不可直接互换。

合成预约的资源占用区间覆盖服务时长与清洁缓冲，订单的 `end_at` 仍表示实际服务结束时间。数据库评测同时检查这两个边界，防止排班或上一笔预约的缓冲时间被漏算。真实门店校准仍需经脱敏且获准使用的数据；若只有业务方提供的分布范围，应将其作为合成参数单独记录。
