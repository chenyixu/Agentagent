### 已完成

### 本轮修掉的关键缺陷（都值得记住）
1. **技能约束不能无差别套到所有资源类型**。房间/设备不携带技能，否则"技师+房间"服务
   会查不到任何候选（表现为无解释的空结果）。现规则：条目自带 `skills` 优先（`[]` 显式豁免）；
   否则服务级 `skills` 只作用于"承载技能的类型"（`load_skill_bearing_types` 按
   `resource_skill` 是否存在数据判定，不写死 `therapist`）；服务级技能要求无法作用到任何
   隐式类型时 **直接报 VALIDATION_ERROR**，不允许静默退化成"技能过滤失效"。
2. **写入路径必须独立复核资源组合**（`catalog.validate_resource_composition`）。
   候选查询只负责构造组合；不做复核的话"技师+房间"能被换成"两间房"。
   失败统一抛 `stale_proposal`，不暴露内部校验细节。
3. **JSONB 存储必须与哈希共用同一套规范化**：新增 `core.hashing.json_safe`。
   否则 datetime 被驱动自行编码后，提交时重算方案哈希会对不上，报"方案哈希校验失败"。
4. **时效裁决时刻必须可注入**：`db.session.live_now(session, clock=None)`，
   生产取 `clock_timestamp()`，测试注入 `FrozenClock`。`expire_due_*` 的谓词
   从硬编码 `clock_timestamp()` 改成 `:now` 参数，由调用方在**拿到锁之后**求值。
   写入函数签名统一为 `(..., now, clock=None)`。
5. **不使用 relationship ⇒ 不能依赖 ORM 隐式 flush 排序**。proposal 与 confirmation
   组合外键之间必须显式 `await session.flush()`；seed.py 同样按依赖分层显式 flush。

### 约定
- `proposal.version = task.version + 1`（任务版本每次乐观锁更新严格递增，故方案版本严格递增）。
- 测试里 `rollback()` 会让 ORM 实例过期，之后再读属性会触发惰性加载 → 先取住需要的 ID。

## 第二轮：工具边界 / Agent 层 / 编排器（任务 4、5 完成）

测试：68 全绿。分布：`test_core_flow.py` 3、`test_resource_requirements.py` 9、

### 本轮修掉的缺陷（编排器从"能跑"到"可信"）
1. **`session.refresh` 静默回退状态**（最关键）。autoflush 关闭时 `refresh` 会丢掉尚未 flush 的
   状态改动，表现为"状态推进了又退回去"，而工具已经执行过。`_reload` 必须先 `flush()`
   再用 `populate_existing=True` 重查。
2. **消息没有落回同一个会话**。`ensure_conversation` 原本每次无 `conversation_id` 都新建会话
   ⇒ 下一条消息开新任务，"第一个可以"永远接不上刚给的候选。现按 (客户, 门店, OPEN) 复用
   最近会话（`store_id.is_not_distinct_from`），显式会话 ID 仍优先。
3. **同一轮里替用户选候选**。`_pick_candidate_index` 默认返回第一个 ⇒ 用户还没说"要哪个"就
   真实占用技师+房间。改为 `detect_candidate_selection`：只认 `第N个`（必须带量词，避免
   "第二天"被读成"第二个"）；单候选时"可以"才算选定；越界/歧义一律返回 None。
   运行时用 `fresh_fact_keys` 区分"本轮刚查出的候选（只展示）"与"用户已看过的候选（可选定）"。
4. **门店停用被描述成"没有号"**：读路径（`search_availability` / `get_service_quote`）原本不校验
   `store.status`，只有写路径校验。新增 `catalog.load_bookable_store`，读路径同样报
   VALIDATION_ERROR；编排器在只读调用全失败时给"查询暂时不可用"而不是"没有可约时段"。
5. **凭据重建与可审计取价的边界**：`_rebuild_followups` 原本无条件预签发报价 ⇒ 首次取价
   绕过工具边界、不留 `tool_execution` 记录。改为：账本里**已有**报价才重签（供占位用），
   首次取价必须走 `get_service_quote` 工具。
6. **事实必须带查询指纹**。候选只在"同一服务+同一时间窗"下有意义，否则用户改时间后
   旧候选会被当成当前方案。`_persistable_projection` 写入 `query_key = content_hash(service+window)`，
   重建时按指纹过滤；槽位真变化时把已算出的事实从 `fresh_fact_keys` 里剔除（只按 `value` 比较，
   来源消息/时间戳变化不算改写）。
7. **PROPOSED 不是终点**：用户在方案上改条件时，`_apply_patches` 把状态退回 SEARCHING
   （PROPOSED→SEARCHING 是合法迁移），再重新取证；`_on_proposed` 也会先解析槽位补丁再谈选择。
8. **PROPOSED→WAITING_USER 不合法**：报价凭据过期时不能追问用户，改为重新调用取价工具。
9. 适配器 `normalize_model_output` 原本不过滤槽位名 ⇒ 模型能带不存在的槽位进流程。
   现按 `ALLOWED_SLOTS` 过滤（领域层仍是权威把关）。

### 新增约定
- `_advance_after_reads` 只在**事实齐备**时推进：COLLECTING 槽位齐 → SEARCHING；
  SEARCHING 有非空候选 → PROPOSED（否则停在 SEARCHING 并如实说明）。
- SEARCHING 阶段只认本次活跃执行里"刚取到"的事实（`fresh_fact_keys`）：账本旧值可能是
  另一个时间窗或旧价格。恢复时宁愿多查一次。
- `PROPOSAL_INVALIDATING_SLOTS = {store, service, time_window}`；`changed` 只比较槽位的 `value`。
- 只读调用整轮全失败 → 立即以 ERROR 结束活跃执行（不再重试同一个调用），并把原因说成
  依赖失败而非"没号"。
- 追问的 `waiting_request.task_version` 记**状态推进之后**的版本（那才是用户看到的版本）；
  记推进前的值会让随后的答复被误判为最新。

## 第三轮：接入层收口（任务 6）与 Worker/投递账本（任务 7）

### 任务 6 完成（API / SSE / 确认 / 查单）
修掉 3 个失败测试时发现的问题，其中 3 个是**真实缺陷**、1 个是测试自身的时钟耦合：

1. **确认路由根本没跑通**：`submit_confirmation` 漏传 `now`，`confirm_appointment` 直接
   `TypeError`。改为 `now=await live_now(session)`（数据库时钟）——凭据有效期、占位期限、
   价目生效窗口都按它裁决。
2. **幂等必须先于版本裁决**（设计稿 §8.2）。确认成功会把 `task.version` 推进一位，所以
   "响应丢失后同键重试"若先去比 `expected_task_version`，必然被**自己的第一次提交**判成
   `VERSION_CONFLICT`——幂等键形同虚设。现在 `register_operation` 排到版本检查之前，
   `handle.is_replay` 时直接重放原订单。加固：`_create_request_payload` 抽成单一函数，
   避免"登记用一份哈希、判定用另一份"。
3. **锁序与声明层次倒挂**：`confirm_appointment` 原本按 task(10) → confirmation(73) →
   proposal(72) → hold(71) 加锁，正好是 §7 声明顺序的逆序，且绕过了 `LockSequencer`。
   现按"先无锁读关系确定集合 → 按 hold(71) → proposal(72) → confirmation(73) 升序加锁并重读"，
   使用已有的 `lock_hold` / `lock_proposal` / `lock_confirmation` 助手。
4. **同一授权换幂等键会撞唯一约束变成 500**：`operation` 表有
   `UNIQUE(tenant_id, confirmation_id)`。`register_operation` 现在在提供 `confirmation_id`
   时也按凭据取回原操作（凭据是比键更强的去重依据），并只在"同一个键"上才判
   `IDEMPOTENCY_MISMATCH`。
5. **`target_appointment_id` 从未回填**，导致查单接口反查不到 CREATE 操作。确认响应直接
   使用 `outcome.operation.id`（权威），并在创建订单后回填操作产出。
6. **SSE 保留窗口的时钟耦合**：事件由编排器时钟盖章、窗口由数据库时钟裁决，两者漂移时
   整条流被判成"窗口外"，每次订阅都返回 RESET_REQUIRED。**这不是保留策略生效，是时钟
   故障冒充业务结论。** 时间维度的锚点改为 `min(now, 流头部事件时刻)`：漂移最多裁掉头部
   之前的历史，永远不会裁掉头部。
7. **请求体形状错误绕过统一错误契约**（FastAPI 默认 `{"detail": [...]}`）。新增
   `request_validation_error_handler`，收敛成 `VALIDATION_ERROR` + `details.fields`，
   于是"请求体里塞 tenant_id"成为可断言的契约事实。

关键取舍：**同一个错误码对应同一个 HTTP 状态码**。设计稿把 `VALIDATION_ERROR` 放在统一
枚举里，所以传输层形状错误也用 400 而不是 422，避免"同一个码两种状态"。

### 任务 7：Worker 与通知投递账本（新增 `src/appointment/worker/`）
- `claims.py`：租约 + fencing。领取时 `fencing_token += 1`；归还必须带 `(owner, token)`；
  不匹配返回 False 而不是抛业务错误（正确语义是"所有权已转移"，不是"业务失败"）。
  领取用 `FOR UPDATE SKIP LOCKED`；`attempt_count` 在**领取时**自增（进程被杀也留痕迹）。
- `providers.py`：供应商端口 + 沙箱。**超时是 UNKNOWN 不是失败**；沙箱支持按键/按顺序
  注入脚本，新增 `ACCEPTED_LOST`（已受理但响应丢失）——这正是对账存在的理由。
- `delivery.py`：三阶段发送「准备并提交 → 事务外调用 → 回来记账」。**调用供应商时不开
  事务**（§7）。内容变化创建更正投递（`template_version` 加 `+revN`），旧行标 SUPERSEDED。
- `receipts.py`：验签 + `provider_event_id` 去重 + **时间/防重放窗口**（`issued_at` 与
  `occurred_at` 必须分开：前者管重放，后者管事件顺序）+ 无映射进 QUARANTINED 队列。
  状态归并走优先级表，**晚到的 ACCEPTED 不降级 DELIVERED**，冲突留痕。
- `runner.py`：outbox → job → delivery 三层。发送 job 只负责"交给供应商并如实记账"，
  推进状态归对账 job。`run_once(reclaim/outbox/jobs/receipts)` 可分段执行。
- `__main__.py`：`python -m appointment.worker` 常驻循环，SIGTERM 只设停止标志、等当前轮跑完。
- 新增回调入口 `POST /v1/provider-receipts/{provider}/{account_id}`：**全系统唯一不带租户
  身份的路由**，身份来自账户配置 + 签名 + 时间窗口；一律返回 200，结论放在 `action`。

### 新增约定（本轮踩到并固化的坑）
- **`finish_job` 的重排不能把 `next_run_at` 写成 NULL**：它是非空列，"没给"与"置空"必须区分。
- **异步测试断言别的会话改过的行，必须 `populate_existing`**。`expire_on_commit=False` 让
  会话身份映射里留着旧对象，断言会读到过期状态——**测试会说谎**，而且失败原因指向被测代码。
- **同一个逻辑待办重复触发要"复位"而不是"跳过"**：`logical_key` 表达的是"哪个待办"而非
  "第几次尝试"，已 SUCCEEDED 就不该永远不再跑（`reset_if_exists`，且要求无租约）。
- **"没有联系方式"不是"已通知"**：留 `alert.manual_followup` 人工待办，不建假装发过的投递。
- 未配置通知渠道时：Outbox 照常消费，但不建投递、不假装发过。

## 第四轮：人工测试就绪度核查 + 两个真实缺陷（15:36 起）

用户问"现在能人工测试了吗"。为回答这个问题**真起进程**跑了一遍，结果在真实进程上
打出两个单测没覆盖的缺陷——记录在这里，因为它们比结论本身更值钱。

### 人工测试暴露的缺陷（已修 + 已加回归测试）

**缺陷 1：事件序号计数器漂移 → 不可自愈的硬失败。**
`emit_task_event` 取 `task.next_event_sequence` 这个**缓存**分配序号，而唯一约束
`uq_task_event_tenant_id_task_id_sequence` 认的是 `task_event` 里已落库的行。两者
一旦脱节（中断的写入 / 历史数据 / 人工修补），每一次 emit 都撞唯一约束。
修复：`sequence = max(task.next_event_sequence, latest_committed + 1)`——多付一次
索引扫描换自愈。注意本会话 autoflush 关闭，同轮 pending 事件查不到，但那时缓存
已经领先，`max` 仍正确。

**缺陷 2：`finally` 里的清理把真实异常盖掉。**
失败把会话打成"待回滚"，`finally: await self._release_lease(ctx, task_id=task.id)`
去碰 `task.id` 触发延迟加载 → `PendingRollbackError` **顶替**了原始 `IntegrityError`，
线上看到的是一个不可读的 500。修复三点：
1. `task_id_for_cleanup = task.id` 在任何可能失败的 ORM 访问**之前**取成纯值；
2. `except BaseException` 里先 `await session.rollback()`（这个事务注定回滚，
   回滚不丢已承诺的效果，却是让清理还能跑得动的前提）；
3. 新增 `_finish_turn_cleanup(..., masked=)`：本轮已在失败 → 清理失败只记录；
   本轮成功 → 清理失败必须抛出。

**验证方式（重要）**：两条回归测试都**先把修复注释掉跑一遍**，确认它们真的失败
（`IntegrityError` / `RuntimeError: 收尾也炸了`），再恢复。走一遍这个流程才知道
测试是不是在测空气。

### 新增开发脚本（人工测试入口）
- `scripts/dev_reset.py`：清库 + 灌 `seed()`，并把身份头直接打印出来。参考时刻取

- `scripts/dev_receipt.py`：造一条**已签名**的供应商回执。不造它，投递账本永远停在

- `人工测试指引.md`：curl 级操作手册 + 已知边界清单。

| `authorization.py` | 授权判定（不碰 I/O，便于单测）：登录名→`ToolScope`、`ToolScope`→身份 |
| `tools.py` | 只读工具装配；身份由闭包捕获 |
| `prompt.py` | 系统提示词，含**能力边界**（必须如实说不能下单） |
| `service.py` | `create_app` 装配、Redis 播种、启动横幅、`__main__` |

三条不变式：业务事实只在业务库；可信身份只来自服务端；作用域必须自洽（框架核对
会话作用域 == 解析出的 `ToolScope`，不等即拒）。

### 踩到并修掉的两个真问题
1. **确定性 bug（测试暴露）**：`load_identities` 原先按 `created_at, id` 排序，而种子的
   两个客户 `created_at` 相同、`id` 是随机 UUIDv4 → `customer-1` 会随机是林女士或赵先生，
   测试约一半概率失败。种子在 `protected_contact_ref` 写了稳定序号
   `hmac:customer-{index}`，改用它排序。**这不是"把联系信息当身份"**——可信身份仍是
   tenant/actor/customer 三个 UUID，只是借它的序号当"第几个客户"的标签。
2. **重置业务库后旧会话不可用**：`seed()` 每次生成新 UUID，而会话作用域不可变 →
   旧会话必然被框架拒绝。在播种时检测作用域不一致就删掉重建；`dev_reset.py` 也加了
   默认清理 Redis 里 `*appointment*` 键（`--skip-redis` 可跳过）。

### 安全边界实测
`manager` 与未知登录名的对话请求虽然返回 200（`/chat/` 是 fire-and-forget），但运行

user 命名空间下建了个空 messages 键。缺 `X-User-ID` 直接 422。
